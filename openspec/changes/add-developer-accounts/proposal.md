## Why

The relay is built to run as a single shared service — ideally on Render or another PaaS — but the consumer onboarding flow today assumes the operator and the developer are the same person on the same machine. Issuing a listener token, registering a push subscription, or even just running `hooksctl forward` requires either an admin token planted in the dev's environment out-of-band or shell access to the host where the relay runs. That is fine for a homelab; it does not work when the relay lives in the cloud and a teammate's laptop comes online for the first time. We need a remote-first developer onboarding loop: a developer creates an account on a deployed relay, logs their CLI in over the network, and starts receiving webhooks — over SSE for ephemeral dev work, over outbound HTTP POST for long-lived consumer services — without an admin running a CLI on the server.

The posture is **secure-by-default with DX escape hatches**: every new surface is invite-gated, narrowly-scoped at the default, rate-limited, and CSRF-protected; power-user shortcuts (long-lived listener tokens, broader scope grants, self-managed push subscriptions) are explicitly opt-in.

## What Changes

- **New `users` identity model.** Listener tokens, push subscriptions, and inspector sessions are owned by a user. The first user is the admin (created by `hooks init` or the existing admin token); additional users are created via signup gated on an admin-issued invite code. There are no public open-signup flows in v1.
- **Password-based web login** at `/login`, with session cookies for the inspector. Argon2id-hashed passwords. Session secret material is stored as SHA-256 of the random session-secret plaintext (not Argon2) — sessions are 256-bit random and do not need Argon2's slowness. Constant-time comparison still applies.
- **CLI device-pairing flow** (`hooksctl login --server <url>`): the CLI requests a device code, prompts the user to visit a URL, polls for approval, and stores the resulting personal access token under `${XDG_CONFIG_HOME:-$HOME/.config}/hooks/credentials.<profile>`. Approval defaults to a narrow `account`-only scope; the CLI may request additional source scopes via `--scopes render,stripe`, and `--admin` is required to mint an admin-scoped PAT. The approver page shows requesting user-agent, IP, and the requested scopes, requires the user to re-enter their password, and lets the approver narrow (but not widen) the scopes before approving. No password ever touches the CLI; works over the network with no shared filesystem.
- **Two distinct token kinds, one row.** `listener_tokens.kind` distinguishes `pat` (manages `/api/me/*` and authenticates the inspector) from `listener` (authorizes `/subscribe/<source>`). Device-pairing mints PATs; `hooksctl me token add --kind listener` and `hooksctl forward` mint listener tokens. PATs cannot subscribe; listener tokens cannot manage `/api/me/*`. This keeps blast radius small.
- **Self-service `/api/me/*` endpoints** for users to issue, list, and revoke their own listener tokens and PATs and to register, list, pause, rotate, and remove their own push subscriptions. The previous `/api/tokens` and `/api/push` endpoints stay admin-only and gain cross-user visibility (admin can see/manage anyone's resources).
- **`hooksctl forward` and `hooksctl push add` work after `hooksctl login` with no token plumbing.** `forward` defaults to minting an ephemeral session-scoped listener token automatically and revokes it on disconnect; power users may pass `--token <id>` to reuse a long-lived listener token. `push add` registers under the logged-in user.
- **Inspector UI grows a user dimension.** Admin sees a `/inspector/users` page (create invite, list users, deactivate, edit `default_scopes`) and can filter tokens/push subscriptions by owner. Non-admin users get a `/inspector/me` view scoped to their own resources. An admin-only `/inspector/audit` surface renders the new audit log.
- **Invite codes** are exposed as both `hooks invite` (server-side) and `hooksctl invite {create,list,revoke}` (remote, hits `/api/invites` using the admin's PAT). Each invite expires after 7 days by default and is single-use. Existing `hooks init` is extended to also print the first signup URL (admin-account creation) when no users exist yet, so a freshly deployed cloud instance is bootstrappable from a browser without shell access — but only via that single bootstrap link, which has a **24-hour TTL** and auto-disables once any account exists.
- **CSRF defenses on every cookie-authenticated mutation.** Every state-changing endpoint that accepts a session cookie (`/api/auth/*`, `/api/me/*`, `/api/users/*`, `/api/invites/*`, admin `/api/tokens` and `/api/push-subscriptions` mutations) checks Origin/Referer and validates a per-session double-submit CSRF token rendered into inspector forms. `Origin: null` is rejected as cross-origin.
- **Rate limiting** on authentication and pairing endpoints (token-bucket per IP, plus per-user buckets where applicable) returns HTTP 429 with `Retry-After`.
- **Audit log** of admin-relevant actions (invite lifecycle, user lifecycle, ownership transfer, password reset, session lifecycle, scope edits) persisted in `audit_events` and surfaced at `/inspector/audit`.
- **Password policy.** Signup and password-reset reject passwords shorter than 12 characters and passwords that contain the user's email. (HIBP integration is a non-goal for v1.)

The change is **additive and does not break existing deployments**: tokens minted by `hooks init` or `hooksctl token add` continue to work without an owning user (treated as system-owned; their existing scopes are preserved verbatim — `owner_user_id=NULL` does not mutate scope assignment) until an operator migrates them.

## Capabilities

### New Capabilities

- `developer-accounts`: User identities, password login with sessions, invite-code signup (including the one-time bootstrap invite emitted by `hooks init`), CLI device-pairing flow with narrow-by-default scopes, password policy, rate limiting on auth surfaces, and per-user self-service management of listener tokens and push subscriptions via `/api/me/*`.
- `audit-log`: Immutable per-action records of admin-meaningful operations, persisted in `audit_events` and rendered at `/inspector/audit` for admin review.

### Modified Capabilities

- `event-subscription`: Listener tokens gain an optional owning user, an explicit `kind` (`pat` vs `listener`), and an optional `expires_at`. Revoking a user cascades to revoking their tokens. Token-creation rules are extended so non-admin users can only mint tokens with scopes they themselves hold. Scope checks are token-level (the bearer's scopes), with a documented translation for cookie-session requests.
- `push-delivery`: Push subscriptions gain an optional owning user; users can manage only their own subscriptions; admins retain full visibility.
- `dev-inspector`: Inspector adds user management for admin and a per-user self-service view; the cookie session model is extended from "admin token in cookie" to "user-session-id in cookie", with admin-token-in-cookie kept as a fallback for ops bootstrap (still authorizes mutations in v1; deprecated in v2). All inspector form POSTs carry a server-rendered CSRF token validated alongside Origin.

## Impact

- **New packages**: `internal/users` (identity, sessions, invites, device pairing, password policy), `internal/audit` (audit-log writer + reader), `internal/ratelimit` (in-process token bucket middleware). API handlers under `/api/me/*`, `/api/auth/*`, `/api/users/*`, and `/api/invites/*`. New CLI subcommands in `cmd/hooksctl`: `login`, `logout`, `whoami`, `me {token,sub} ...`, `invite {create,list,revoke}`. New CLI subcommand in `cmd/hooks`: `invite`.
- **Storage additions**: `users`, `user_sessions`, `invites`, `device_pairings`, `audit_events` tables. `listener_tokens` gains `owner_user_id` (nullable FK), `kind` (`'pat'|'listener'`, default `'listener'`), `ephemeral` (BOOL DEFAULT 0), `expires_at` (nullable). `push_subscriptions` gains `owner_user_id` (nullable FK). `device_pairings` records `requested_scopes`, `requesting_ip`, and `user_agent` to support the approval flow.
- **Storage code generator**: this change introduces [sqlc](https://sqlc.dev) (`engine: sqlite`) as the source of truth for SQL queries. The full canonical schema lives in `internal/store/schema.sql` (deliberately *outside* the `queries/` directory so sqlc does not double-parse it); queries live in per-domain `internal/store/queries/*.sql` files annotated with `:one`/`:many`/`:exec`/`:execrows`; sqlc generates `internal/store/sqlcgen/` with a `*Queries` type and per-row `models.go` structs that the existing `internal/store` package wraps to preserve the public `EventStore`/`TokenStore`/`PushSubscriptionStore` interfaces and add the new `UserStore`/`SessionStore`/`InviteStore`/`DevicePairingStore`/`AuditStore` interfaces. The wrapper layer owns the `*sql.DB` pool, runs schema migration on boot, and is the only place that translates between sqlc's `database/sql` null/int types and the public types' `*time.Time`/`[]string`. The sqlc binary is pinned via Go 1.24+'s `tool` directive (`go get -tool github.com/sqlc-dev/sqlc/cmd/sqlc@latest`) so contributors run `go tool sqlc generate` without a side-loaded install. **Rationale:** compile-time-checked SQL across the entire storage layer; new queries (owner-filtered token/subscription lookups, cascading deactivation, audit insert) get the same type safety as old ones; mixing sqlc for new tables with hand-rolled SQL for old tables would be a worse end-state. Adopting it for the whole store is in scope for this change. See `design.md` for layout, type-mapping conventions, and the transaction pattern.
- **Config**: a single new optional knob `web.session_ttl` (default 30d) and a new optional `web.trust_proxy_headers` (default `false`) gating recognition of `X-Forwarded-Proto` for the `Secure` cookie flag. No new YAML required for default deployments.
- **Wire-format additions**: new endpoints listed above. `Authorization: Bearer <token>` continues to work for both system tokens and user-issued PATs/listener tokens; cookie sessions carry a session id (server-side lookup with SHA-256 secret comparison) rather than the raw bearer.
- **Inspector**: HTML templates and embedded static assets gain a login form, an account-management page, a per-user landing page, an audit-log page, and CSRF-token inputs in every mutation form. No change to the existing event-browsing UI other than an "owner" column where appropriate.
- **No change** to the inbound `/ingest/<source>` surface, the verifier plugin model, the event store, the push dispatcher loop, or the on-disk body-bytes-are-sacred contract.
- **Backwards compatibility**: existing tokens continue to authenticate with their existing scopes and a NULL `owner_user_id` (treated as system-owned). Cookie-based admin login by raw bearer token is preserved (full mutation access in v1). Operators who never issue an invite continue to use the relay exactly as today.
