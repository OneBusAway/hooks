## 1. Schema migrations and storage primitives

All new and altered tables live in `internal/store/schema.sql` (the canonical schema authored in §0.3). The tasks below describe the *content* of that file plus the upgrade-only deltas that bring existing v1 deployments forward; the SQL itself is part of §0, not separate migration files.

- [x] 1.1 In `schema.sql`, add the `users` table (id TEXT PRIMARY KEY, email TEXT NOT NULL, name TEXT NOT NULL, role TEXT NOT NULL CHECK (role IN ('admin','user')), password_hash TEXT NOT NULL, default_scopes TEXT NOT NULL DEFAULT '[]', created_at INTEGER NOT NULL, deactivated_at INTEGER, external_id TEXT). Case-insensitive uniqueness on `email` is enforced by a separate `CREATE UNIQUE INDEX IF NOT EXISTS idx_users_email_nocase ON users(email COLLATE NOCASE)` (declared alongside the other indexes in §1.8). Inline `TEXT UNIQUE NOCASE` is *not* valid SQLite column-constraint syntax — `NOCASE` is a collation that must be introduced with the `COLLATE` keyword, and tying it to UNIQUE is reliable only via an explicit unique index.
